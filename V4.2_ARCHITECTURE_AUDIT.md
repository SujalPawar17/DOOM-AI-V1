# DOOM V4.2 — ARCHITECTURE & RELIABILITY AUDIT

**Audit Date**: 2026-09-06  
**Audited Baseline**: DOOM V4.1 (`v4.1.0`, Commit `4661c70`)  
**Target Milestone**: DOOM V4.2 Production Hardening  

---

## 1. Current Authoritative Production Path

The production execution path established in DOOM V4.1 has been confirmed as the sole path:
```text
Client / CLI / Voice / REST API / HUD
                ↓
    DOOMCore.process_request()
                ↓
    self.cognition.process()
                ↓
    [UNDERSTAND → REASON → DECIDE → PLAN]
                ↓
        CognitiveBridge
                ↓
TaskEngine + StateMachine + ModelRouter + ToolRegistry
                ↓
        [ACT → OBSERVE → EVALUATE]
                ↓
    [REFLECT → (REPLAN if needed)]
                ↓
        GroundTruthVerifier
                ↓
    Truthful Final Response & Memory 2.0
```

There are no duplicate active orchestrators. However, several critical resilience, idempotency, concurrency, and validation gaps were identified across the integration boundary.

## 2. Identified Reliability Risks & Vulnerabilities

| ID | Component | Vulnerability / Risk | Severity |
|---|---|---|:---:|
| **R-01** | Tool Execution | **Missing Formal Idempotency Ledger**: While `DecisionEngine` tracks action signatures in memory, it lacks an authoritative, durable idempotency ledger that claims a key before execution, tracks in-flight pending operations, stores execution receipts with return values and artifacts, and resolves duplicate requests safely. | **HIGH** |
| **R-02** | Retry Loop | **Blind Retries Without Prior Verification**: If a side-effecting tool (e.g. writing a script or running a command) times out or encounters a transient error, retrying without checking if the external artifact was already created can produce duplicate writes or corrupted state. | **HIGH** |
| **R-03** | Retry Budget | **Scattered / Unbounded Retry Counters**: Retries exist ad-hoc across `DecisionEngine`, `model_router`, and `bridge.py`. There is no central, unified retry policy bounding per-step, per-task, wall-time, and timeout budgets. | **HIGH** |
| **R-04** | Cognitive Loops | **Loop Cycling Vulnerability**: While `bridge.py` caps cycles at `MAX_COGNITIVE_ITERATIONS = 5`, it does not detect repeated identical failures, identical replans, or ping-ponging between identical states. | **MEDIUM** |
| **R-05** | Plan Generation | **Unvalidated Cognitive Plans**: Plans generated by `CognitiveEngine` are executed by `CognitiveBridge` without pre-execution validation for unique step IDs, acyclic DAG dependencies, tool existence, argument schemas, or resource bounds. | **HIGH** |
| **R-06** | Tool Boundaries | **Model Tool Argument Poisoning & Path Traversal**: Model-generated arguments are passed directly to tools without a rigorous boundary validator checking for path traversal (`../`), dangerous system commands, or type/range violations. | **HIGH** |
| **R-07** | Task Concurrency | **No Task Lock / Lease**: Two concurrent requests or workers can attempt to execute the same task ID simultaneously, resulting in race conditions and corrupted checkpoints. | **HIGH** |
| **R-08** | Crash Recovery | **Incomplete Post-Crash State Reconciliation**: If the process terminates after a side effect is executed on disk but before a checkpoint or response is saved, restart recovery currently lacks a reconciliation step to inspect idempotency receipts and external disk state. | **HIGH** |
| **R-09** | Checkpoint Schema | **Missing Contextual Metadata**: Checkpoints do not comprehensively record idempotency keys, correlation/trace IDs, security decisions, or granular evaluation diagnostics. | **MEDIUM** |
| **R-10** | Cancellation | **No Formal Cancellation Lifecycle**: `TaskEngine` has `TaskStatus.CANCELLED` but lacks a formal `cancel_task()` method with `RUNNING -> CANCELLING -> CANCELLED` transition, active execution draining, and side-effect reconciliation. | **MEDIUM** |
| **R-11** | Approval Races | **Unbound Approvals**: Approvals in `TaskEngine.pending_tool_call` are not cryptographically bound to operation IDs, risk levels, and timestamps, creating vulnerability to stale approvals or changed actions. | **HIGH** |
| **R-12** | Model Router | **Missing Circuit Breaker**: Repeated failures against an unavailable provider hammer the endpoint without an automated circuit breaker (cooldown window / half-open probe). | **MEDIUM** |
| **R-13** | Memory Safety | **Unverified Episode Persistence**: If a task fails verification or is aborted, any partial state must not be recorded as a successful episodic memory. | **MEDIUM** |
| **R-14** | Observability | **Missing Trace / Correlation IDs**: Requests lack an end-to-end trace context (`doom_request_id` -> `task_id` -> `cycle_id` -> `step_id` -> `operation_id` -> `tool_execution_id`). | **MEDIUM** |

## 4. Proposed Fixes & Architectural Plan

### Phase 1 — Durable Idempotency
- Implement `IdempotencyManager` storing receipts with `idempotency_key = hash(task_id + step_id + action + canonical_args)`.
- Keys are claimed as `PENDING` before tool execution. On success, receipts store artifacts, outputs, and exit codes. On duplicate call with the same key, the cached receipt is returned immediately without executing the tool.

### Phase 2 — Verify-Before-Retry
- When a tool fails or times out, determine if the side effect may have already occurred (e.g. file exists on disk with expected contents).
- If ground truth confirms the effect happened, reconcile and mark step `SUCCEEDED` instead of repeating the write.
- If state is ambiguous, mark `RECONCILIATION_REQUIRED` / `UNKNOWN` and stop.

### Phase 3 — Authoritative Retry Policy
- Define `RetryPolicy` with strict budgets:
  - `MAX_RETRIES_PER_STEP = 2`
  - `MAX_TOTAL_RETRIES_PER_TASK = 5`
  - `MAX_COGNITIVE_REPLANS = 3`
  - `MAX_TOOL_TIMEOUTS = 2`
  - `MAX_TASK_WALL_TIME = 120.0s`
- Separate retryable transient errors (network timeouts, rate limits) from non-retryable fatal errors (security blocks, syntax errors, invalid arguments).

### Phase 4 — Cognitive Loop Defense
- Track consecutive failure counts, identical plan signatures, and repeated action patterns in `CognitiveBridge`.
- If 2 consecutive replans generate identical steps or 3 consecutive steps fail with the same root cause, abort the loop and transition to `FAILED` or `PAUSED`.

### Phase 5 & 6 — Pre-Execution Plan & Input Validation
- `PlanValidator` inspects plans before execution: validates step dependencies form a directed acyclic graph (DAG), tool names exist in `tool_registry`, step counts do not exceed bounds.
- `ToolInputValidator` inspects arguments before tool invocation: enforces path safety (no `../` traversal, root directory escapes), sanitizes dangerous terminal commands, validates expected types.

### Phase 7 & 8 — Concurrency & Crash Recovery
- Implement file-backed and memory-backed `TaskLease` ensuring only one worker executes a task at any moment.
- If a process crashes and restarts, `TaskEngine.recover_task()` inspects durable checkpoint, loads idempotency receipts, reconciles external file state, and resumes from the exact unexecuted step.

### Phase 9 & 10 — Hardened Checkpoint & Safe Cancellation
- Checkpoints include all execution receipts, idempotency keys, verification proofs, and correlation IDs.
- Cancellation transitions `RUNNING -> CANCELLING -> CANCELLED`, drains running step safely, and marks remaining steps cancelled.

### Phase 11 & 12 — Approval Binding & Provider Circuit Breakers
- User approvals are stamped with `operation_token = hash(task_id + step_id + tool + args)`. If arguments or tool change, the token is invalid and re-authorization is demanded.
- Model router tracks provider error rates: 3 consecutive failures trip the circuit breaker into `OPEN` state for a 60-second cooldown, routing to the next capable provider.

## 5. Invariant Preservation Plan

1. **INVARIANT 1 (One Task = One Authoritative State)**: `TaskEngine` and `StateMachine` remain the single source of truth.
2. **INVARIANT 2 (One Side Effect = One Operation)**: `IdempotencyManager` guarantees side effects cannot be executed twice.
3. **INVARIANT 3 (Model Belief != Reality)**: `GroundTruthVerifier` has ultimate completion veto power.
4. **INVARIANT 4 (Completed Steps Never Repeated)**: Resumes and retries strictly check completed step indices and receipts.
5. **INVARIANT 5 (Unknown != Success)**: Unverifiable external states are marked `RECONCILIATION_REQUIRED`.
6. **INVARIANT 6 (Failure Must Be Visible)**: Timeouts and errors are never mapped to success.
7. **INVARIANT 7 (Security Cannot Be Bypassed)**: Risk checks precede all tool execution gates.
8. **INVARIANT 8 (No Unbounded Autonomy)**: Central retry budgets and cognitive loop bounds strictly terminate execution.
9. **INVARIANT 9 (No Duplicate Orchestration)**: `DOOMCore.process_request()` -> `CognitiveEngine.process()` -> `CognitiveBridge` remains the only path.
10. **INVARIANT 10 (Deterministic Recovery)**: State is reconstructed purely from durable checkpoints and verified receipts.
