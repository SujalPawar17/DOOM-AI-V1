# DOOM V12.6 — Real-Time Cognitive Loop: Implementation Report

**Date:** 2026-10-04 · **Branch:** DOOM-V10 · **Base:** `3f460c4` (`V12.5-FREEZE`)

## 1. Architecture

```
Event sources: timers | system | monitored goals (V11.5) | applications | integrations | user
  -> RuntimeEvent (normalized: owner, session, source, type, priority, bounded scalar payload,
                   deterministic dedup key)
  -> submit(): dedup (5 min window, ≤1024 keys) -> cooldown per (owner, source, type)
               (CRITICAL bypasses) -> per-owner quota (32) + global bound (128)
               -> priority-aware backpressure (only strictly lower priority is evicted)
  -> single worker: run_once(budget=8): due timers -> rate limit (12 cycles/min)
               -> circuit breaker (3 consecutive failures -> 60 s pause) -> handler
  -> CognitiveEventHandler: perceptual SYSTEM_EVENT update -> V12 cognitive cycle with
               monitoring context -> outbox (≤64, owner/session-scoped)
```

## 2. Safety and control properties

- **No uncontrolled autonomy:** the handler only runs monitoring-flagged cognitive cycles. Any plan goes through the unchanged Cost Guard, authorization and verification chain; approval-requiring actions stop at `APPROVAL_REQUIRED` (tested with a real V8 executor path). Results go to an outbox; nothing is auto-approved or auto-spoken.
- **Not learned as user statements:** monitoring-flagged input is excluded from V12.2 statement learning (tested).
- **Bounded everything:** queue, per-owner quota, dedup memory, outbox, timers (≥1 s interval, no catch-up bursts), per-tick work budget, per-minute cycle budget.
- **No infinite loops or thread leaks:** one worker; every wait has a timeout; `stop()` joins with a bound and reports a still-running handler honestly; `start()` is idempotent; `restart()` works. A 5× start/stop cycle leaves no threads (tested).
- **Fault recovery:** handler exceptions are contained and recorded in the outbox. The circuit breaker pauses processing instead of burning through the queue, then resumes.
- **Owner/session isolation:** identity is carried per event; quotas stop one owner from starving another; the outbox is filtered by owner and session.

## 3. V11.5 integration (no duplication)

`make_runtime_monitor(runtime, owner, session)` returns the **existing** V11.5 `ContinuousMonitoringEnhancement`, subclassed to override only `_handle_monitoring_event`. Detected events go into the runtime queue instead of spawning a thread per event. All V11.5 detection, fingerprinting, dedup, cooldown and rate limiting are reused, and V11 code is unchanged.

## 4. Files

New: `core/v12/runtime.py`, `test_v12_6_realtime_runtime.py` (14 tests).

## 5. Limitations

- The runtime isn't started by any production entry point yet (unified-OS phase).
- Cycles run synchronously in the single worker, so a slow local-model answer delays later events. That's bounded by the per-tick budget and the V8 responder timeout.
