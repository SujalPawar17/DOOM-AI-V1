# DOOM V11.9 — Performance / Reliability / Long-Session Hardening: Implementation Report

**Date:** 2026-10-04 · **Branch:** DOOM-V10 · **Base:** `1c738a4` (V11.8 freeze)

V11.9 hardens the accepted V11 architecture for long sessions **without redesign**. Every change below fixes a defect that was found by inspection or measurement, and each one has a deterministic regression test in `test_v11_9_reliability_long_session.py` (25 tests).

## 1. Defects found and fixed

| # | Component | Defect (evidence) | Fix |
|---|---|---|---|
| R1 | `core/v10/context_fusion.py` SYSTEM source | **~86% of every cognitive cycle was a hard 1 s sleep.** cProfile: `psutil.cpu_percent(interval=1)` inside `core.advanced_automation.get_system_info()`, and the value was discarded (cpu/memory are fixed to 0 for determinism). | Non-blocking probe of the same psutil subsystems (`virtual_memory`, `disk_usage`). Output keys and values are unchanged. `advanced_automation.py` is untouched. **Cycle: 1,165 ms → 156 ms (profiled).** |
| R2 | `core/v10/context_fusion.py` OUTCOME source | Undefined name `victim_text`: any V11.2 failure experience (blocker `failed_step:<id>`) raised NameError, so **OUTCOME context silently became `{}` after any execution failure**. | `victim_text` → `user_note_text` (the evidently intended variable). |
| R3 | `core/v10/context_fusion.py` GOAL_STATE source | Read `intent`, `capability_class`, `provenance`, `requested_unix_ms`, `goal_hash`, `session_id` and `computer_session_id` from `GoalSnapshot`, which has none of them. AttributeError → **GOAL_STATE (active goal and recent experiences) empty whenever a registry goal is ACTIVE**. | Optional fields are included only when present, so ACTIVE_GOAL source values (lower precedence) are not overwritten with blanks. |
| R4 | `core/v10/context_fusion.py` diagnostics | Unconditional `print` of **every source's full data** (user-model entries and personal memories) to stdout on every cycle: a privacy and performance problem. | `_debug()` is opt-in via `DOOM_CONTEXT_FUSION_DEBUG`, and logs key names and exception types only, never values. |
| R5 | `core/v11/advanced_memory.py` cache | Unbounded: every distinct query added an entry, and expired entries were never purged. | Expired entries are purged on write, then oldest-first eviction above `cache_max_entries = 256`. Copies are returned, so callers can't corrupt the cache. The cache has an RLock (shared by the monitor thread and user cycles). |
| R6 | `core/v11/advanced_memory.py` cache key | **Owner-isolation bug:** key `f"{owner}:{query}:{session}:{project}"` let owner `a`/query `b:x` collide with owner `a:b`/query `x`, a crafted cross-owner cache hit. | Tuple key `(owner, query, session, project)`. |
| R7 | `core/v11/advanced_memory.py` + orchestrator | Stale memory: retrievals were cached for 5 min, so the next cycle could miss a just-recorded experience. | `invalidate_owner_cache(owner)` is called by the orchestrator after a successful experience record. It is owner-scoped only. |
| R8 | `core/v11/proactive_behavior.py` monitor | One **untracked daemon thread per event**: no concurrency bound, and `stop()` did not wait for in-flight cycles. | At most one tracked cycle thread. Events arriving while it runs are skipped (`cycles_skipped_busy`). `stop()` joins it (bounded 10 s). `get_status()` reports `cycle_in_flight`. |
| R9 | `core/v11/cognitive_orchestrator.py` approvals | Since V11.8 each APPROVAL_REQUIRED cycle stashed a **new** V8 pending record, which is never purged. A re-proposed plan (e.g. by the proactive monitor) grew the store without bound. | Reuse the still-live `pending_id` for the identical (owner, session, computer session, plan hash), validated via V8 `pending_display`. A new entry is created only after consume, expiry or revoke. The map is bounded to 256. V8 `authorization.py` is untouched. |
| R10 | `core/v11/cognitive_orchestrator.py` | `cycle_count` incremented without a lock while cycles can run concurrently (user + monitor). | `_state_lock` around the counter. Cycle IDs are unique under 8-thread concurrency. |

The V11.8 test harness `_SyncThread` gained `is_alive()`/`join()` so it satisfies the monitor's new thread-tracking contract (test-only change).

- `core/v10/context_fusion.py`: R1–R4 only.
- `core/v11/advanced_memory.py`: R5–R7.
- `core/v11/proactive_behavior.py`: R8. The file already had mixed CRLF/LF line endings; edits preserve each line's existing ending.

## 3. Test coverage (`test_v11_9_reliability_long_session.py`, 25 tests)

| Area | Tests |
|---|---|
| Long session | 120 mixed cycles: 80 succeed, 20 fail, 20 non-plan; 0 exceptions; no thread growth; memory growth measured; experience bound. 8-thread × 10 concurrent cycles. Re-initialized orchestrator. |
| Context fusion | 100 repeated fusions → identical hash, no stdout. Debug opt-in never prints values. SYSTEM source never blocks (R1). OUTCOME after failures (R2). GOAL_STATE with an active goal (R3). |
| Memory cache | Bounded after 600 queries. TTL purge. Hit plus owner-only invalidation. Crafted-key isolation (R6). Mutation safety. 6-thread concurrent access. Orchestrator invalidates only after experience (R7). |
| Monitor | Busy cycle never stacked (R8). 20× start/stop without thread leak. Cooldown and rate limit (200 simulated events → 5 cycles). Event dedup bounded at 150. |
| Authorization | 50 identical approval requests → 1 pending entry (R9); fresh entry after consume. Identity-scoped reuse (other session cannot claim). Bounded reuse map. |
| Failure / recovery | 40 alternating failure/success cycles. Adapter exceptions don't poison later cycles. Two-owner 60-cycle isolation (store and fused context). |

## 5. Known limitations / residual items (documented, not changed)

- **V8.28 experience store** keeps superseded rows. *Active* records are capped at 64 per owner, but total retained rows grow by one per executed plan (100 after 100 plans). This is V8 behaviour and is left unchanged.
- **V8 authorization store** never purges consumed or expired records. R9 bounds growth from repeated identical proposals, but distinct plans still add one record each. This is V8 behaviour and is left unchanged.
- **PostgreSQL connection churn:** each cycle opens several pooled connections and re-runs `ensure_personal_memory_schema` (~0.1 s), the next-largest cost after R1. This is a V5/V8 DB layer issue, not changed in V11.9.
- `str(GoalLifecycle)` is truncated to `"GoalLifecycle.AC"` in GOAL_STATE (V10 data-quality quirk, not changed).
- V10.2 user-model tests need `PROACTIVE_V827_USER_MODEL_ENABLED`. The test-harness fix is scheduled for the V11.10 audit.
