## 1. Existing Memory Implementation Analysis

### 1.1 Current memory/ Package

| File | Description | Issues |
|---|---|---|
| `memory/__init__.py` | Exports 4 singletons: `user_profile`, `short_term_memory`, `episodic_memory`, `semantic_memory` | No unified interface |
| `memory/user_profile.py` | JSON-file + PostgreSQL user profile with preferences, projects | No confidence, source, or privacy metadata |
| `memory/short_term.py` | In-memory 15-turn sliding window conversation buffer | **Ephemeral only** — not persisted across restarts |
| `memory/episodic.py` | JSON-file + PostgreSQL episode log (goal/plan/tools/outcome/success) | No memory_type enum, no verification_status, no provenance |
| `memory/semantic.py` | JSON-file + PostgreSQL key-value facts store | No confidence, source tracking, or supersession |

### 1.2 Existing PostgreSQL Schema

| Table | Purpose | Missing for V5.1 |
|---|---|---|
| `user_profiles` | One-row profile per user | No memory_id, no privacy_class, no history |
| `episodic_memory` | Raw episode log | No typed MemoryRecord, no confidence, no supersession |
| `semantic_facts` | Key-value facts | No source, confidence, verification_status, privacy_class |
| `system_telemetry` | Hardware metrics | Not memory-relevant |
| `command_logs` | Audit log of commands/responses | Not memory — telemetry only |
| `task_checkpoints` | V3.3 task persistence | Not memory — operational only |

**Critical Gap**: There is NO canonical `memory_records` table with uniform type/status/source/confidence/provenance.

### 1.3 Existing Memory Retrieval

**`CognitiveEngine.retrieve_relevant_memory()`** (engine.py L52-70):
- Pulls `user_profile.get_name()/get_role()` only when keywords like "who/name/me/profile" appear.
- Pulls fixed `semantic_memory` keys ("assistant", "voice", "os", "capabilities") when "doom/system/status" appears.
- **No episodic retrieval** in current path.
- **No confidence or relevance scoring**.
- **No project or task context matching**.
- **No type-based filtering**.

### 1.4 Existing Memory Writes

**Bridge (bridge.py L602-619)**:
- `short_term_memory.add_assistant_turn()` — ephemeral, in-memory only.
- `episodic_memory.record_episode()` — stores raw plan/outcome, only when `is_empirically_successful`.
- No PREFERENCE, PROJECT, EXPERIENCE memory types.
- No supersession logic.
- No confidence tracking.
- No privacy classification.

**Episodic write (episodic.py L21-48)**:
- Records even failed tasks via `success=False` (no hard gate in legacy path).
- Dual-persists to PostgreSQL (`episodic_memory` table).
- Caps local file at 100 episodes (silently drops old ones).

**Semantic write (semantic.py L39-52)**:
- No source tracking — any caller can store any "fact".
- Dual-persists to PostgreSQL (`semantic_facts` table).
- Overwrites existing facts without supersession.

### 1.5 Existing Privacy / Security Controls

- **None** in memory layer. No `privacy_class` field anywhere.
- No access checks on memory reads.
- `user_profile` contains sensitive preferences but no privacy labels.
- Secrets are NOT (currently) stored in memory — but there is no enforcement mechanism preventing it.

### 1.6 Existing Memory/Task Integration

- Memory writes happen at **step 8** (after ground-truth verification) in `bridge.py`.
- `is_empirically_successful` gate: only verified successes go into episodic memory as `success=True`.
- But failed tasks still go in (with `success=False`) — no filter for partial/blocked outcomes.

### 1.7 Existing Memory Serialization

| Component | Format | Location |
|---|---|---|
| Episodic | JSON file + PostgreSQL | `memory_episodes.json` / `episodic_memory` table |
| Semantic | JSON file + PostgreSQL | `memory_semantic.json` / `semantic_facts` table |
| User Profile | JSON file + PostgreSQL | `memory_profile.json` / `user_profiles` table |
| Short-term | In-memory only | Lost on restart |

## 2. Integration Points Identified

### 2.1 Where Memory Is Read (V4.2)
- `CognitiveEngine.process()` → `retrieve_relevant_memory()` → `state.relevant_memory` (dict, raw)
- `reasoning_engine.reason()` receives `relevant_memory` as a dict

### 2.2 Where Memory Is Written (V4.2)
- `CognitiveBridge.execute_plan()` → `episodic_memory.record_episode()` (after verified task)
- `CognitiveBridge.execute_plan()` → `short_term_memory.add_assistant_turn()` (every response)
- `orchestrator._finalize_and_log()` → `episodic_memory.record_episode()` (legacy path, rarely triggered now)

### 2.3 WebSocket / Events (V4.2)
- `CognitiveEngine._broadcast()` → registered broadcaster → all connected WebSocket clients
- Events: `COGNITION_STARTED`, `UNDERSTANDING_COMPLETE`, `REASONING_COMPLETE`, `DECISION_MADE`, `PLAN_CREATED`, `VERIFICATION_COMPLETE`, `COGNITION_COMPLETED`
- **No memory-specific events** exist yet.

### 2.4 API Routes (V4.2, from dashboard/server.py)
- `/api/memory` — serves raw episodic episodes for dashboard
- No structured memory CRUD exists yet

## 4. Architecture Decisions

### 4.1 Database Strategy
- **Extend PostgreSQL** (existing `database/postgres_db.py`). Do NOT introduce Redis, SQLite, or vector DBs.
- Add one new table: `memory_records` with canonical MemoryRecord schema.
- Preserve all existing tables (no migration of existing data into new schema for compatibility).

### 4.2 Memory Package Structure
```
memory/
    __init__.py          ← Update exports (backward-compatible)
    types.py             ← MemoryType, MemoryStatus, MemorySource, ConfidenceLevel, VerificationStatus, PrivacyClass
    schemas.py           ← MemoryRecord dataclass, MemoryContext dataclass
    manager.py           ← MemoryManager (single authority: store/retrieve/update/supersede/archive/delete)
    repository.py        ← PostgreSQL persistence (memory_records table)
    retrieval.py         ← MemoryRetriever (relevance-filtered retrieval)
    ranking.py           ← MemoryRanker (score = relevance + importance + recency + confidence)
    policy.py            ← MemoryWritePolicy (worthiness gate, secret rejection, type classification)
    context.py           ← MemoryContextBuilder (MemoryContext assembly)
    lifecycle.py         ← MemoryLifecycleManager (archive, expire, decay)
    writers.py           ← Typed write helpers (write_experience, write_preference, write_project)
    validators.py        ← MemoryValidator (field constraints, secret detection, content gates)
    # Keep existing files as-is (backward compat):
    user_profile.py      ← Unchanged (existing V4.2 interface preserved)
    short_term.py        ← Unchanged
    episodic.py          ← Unchanged (legacy write path still used for compatibility)
    semantic.py          ← Unchanged
```

### 4.3 Integration Strategy
- `CognitiveEngine.retrieve_relevant_memory()` → replaced with `MemoryRetriever.retrieve()` → returns `MemoryContext`
- `CognitiveState` gets a new `memory_context: Optional[MemoryContext]` field
- `CognitiveBridge` writes through `MemoryManager` after verified task completion
- Memory failure must NOT propagate to task status (try/except with telemetry)

### 4.4 API Strategy
- Add memory API routes to `dashboard/server.py`:
  `GET /api/v2/memory`, `GET /api/v2/memory/{id}`, `POST /api/v2/memory`,  
  `PATCH /api/v2/memory/{id}`, `DELETE /api/v2/memory/{id}`, `POST /api/v2/memory/search`
- Keep existing `GET /api/memory` (legacy episodic read) unchanged

## 5. Audit Verdict

**Pre-implementation baseline is sound. V4.2 is stable. No regressions permitted.**

Key risks:
1. Circular imports between `memory/` and `core/cognition/` — must use deferred imports as already done in bridge.py.
2. PostgreSQL schema migration must use `CREATE TABLE IF NOT EXISTS` and `ADD COLUMN IF NOT EXISTS` — safe to run multiple times.
3. Memory write failure must never propagate to TaskEngine completion status.
4. `CognitiveState.relevant_memory` is currently a plain `Dict[str, Any]` — backward compat needed during transition.
